# Epic 5 Retrospective: Failure-UX Modes & Auto-Fix

## Summary

Epic 5 ships the entire failure-UX surface that the PRD's "Failure modes are first-class UX" theme calls for: a complete `src/failure-ux/` mid-tier module group with four per-handler files (`retry.ts`, `skip.ts`, `route-to-fixer.ts`, `escalate.ts`) plus a fifth pure-function `resolve-policy.ts` resolver, all dispatched via a single `dispatchFailureUx(handler, context)` switch in `src/failure-ux/index.ts`. Story 5.1 introduced the retry-then-escalate handler at the lock-held mid-tier `verify-and-advance.ts` boundary (preserves AR8 lock-free top-tier `runLoop`), wrapping the verifier call site with a maxRetries=2 (3 total attempts) loop and writing typed `runHistory[]` entries (RunHistoryEntrySchema NEW per Story 4.8 CheckpointEntrySchema precedent). Story 5.2 wired the `--skip` failure mode for `/bmad-next` — added the `--skip` flag to NextArgsSchema (19th flag), added `enforceSkipRequiresResume()` cross-validation, performed three simultaneous state mutations (runHistory[].skipped:true + lastSuccessfulStep advance via DAG resolver + lastAttempted clear) under the lock-held atomic-write contract, and added the SOLE NEW error class of the entire epic — `SkipRequiresResumeError` (registry 16 → 17) — necessitated by AC line 1080's verbatim hint string mandate. Story 5.3 added the route-to-fixer mode + `--auto-fix` flag, the NEW `agents/bmad-step-fixer.md` (BYTE-IDENTICAL description to AC line 1091 substring), staging directory layout (`staging/<runId>/` PRESERVED + `staging/<runId>-fix/` deterministic suffix), and the two-entry `runHistory[]` semantic for escalate-after-fix-fail (forensic clarity + Story 6.6/6.7 telemetry-filter compatibility).

Story 5.4 closed the four-handler module group by formalizing the escalate handler with a `ACTIONABLE_HINT_REGEX = /^.*(Run|See|Try|Check) /` PASS-THROUGH+SHAPE contract, four invocation sites in `verify-and-advance.ts` (retry-cap site / SIGINT mid-route-to-fixer / post-fix-fail / defensive unexpected-outcome), and a NEW `src/integration/escalate-actionable-hint.test.ts` with three describe blocks (registry sweep over 17 classes + table-driven over 12 escalate paths + e2e over 3 paths) — codifying the errors-as-primary-UX contract at the integration test level. ## Lessons Learned

- **The mid-tier handler-per-file + dispatcher-switch pattern is the canonical shape for failure-UX**: the `src/failure-ux/` module group grew from 0 files to 6 files (4 handlers + dispatcher + resolver) across 6 stories without a single architectural refactor. Each handler is pure-function (no I/O imports); composition + I/O lives at the lock-held mid-tier `verify-and-advance.ts` boundary. The dispatcher's TypeScript exhaustiveness check (no-default-clause switch over the closed FailurePolicy enum) ENFORCES coverage on future variant additions at compile-time. Recommended pattern for any future module group with >2 variants of the same shape.

- **Cross-story coordination via opts.* seam declaration is the cleanest blueprint for multi-story config wiring**: Story 5.6 ships SCHEMA + RESOLVER + tests but DEFERS the FILE LOADER to Story 6.1. By DECLARING the `opts.config` seam on all THREE option interfaces (LoopOpts, RunNextOptions, RunVerifyAndAdvanceOptions) at Story 5.6 time, Story 6.1's file loader becomes a TRIVIAL drop-in — no resolver-API change needed. This pattern scales naturally to Stories 6.3 (models), 6.4 (budgets), 6.5 (verifiers): each can SHIP its schema + resolver in a Story 6.x and have Story 6.1 populate the opts.config seam from disk. Lesson: when a story spans the schema/resolver/loader axis, ship schema+resolver in one story + declare seams + ship loader in the next story.

- **Schema tightening (z.unknown() → typed entry) is a low-risk back-compat-preserving refactor**: Story 5.1 tightened `StateV1Schema.runHistory[]` from `z.array(z.unknown()).max(100)` to `z.array(RunHistoryEntrySchema).max(100)` while preserving 6 legacy optional fields per D1 — back-compat with Story 4.5 token reader + Story 4.x plan-walk consumers (verified at run.ts:1162 + plan.ts:194). Stories 5.2 + 5.3 then added MORE optional fields (skipped, fixAttempt) without breaking anything. Lesson: defence-in-depth schema tightening is a strong pattern when migrations are not desired — preserve legacy fields as optional, tighten new fields strictly.

- **Errors-registry discipline pays dividends but allows AC-mandated exceptions**: Epic 4 retro Recommendations item 3 prescribed "Epic 5 should NOT add new error classes — registry stability discipline established across Epics 2/3/4 (16 codes throughout)". Epic 5 honored this in 5 of 6 stories (registry held at 17 after Story 5.2's single growth). The SOLE deviation (Story 5.2 SkipRequiresResumeError) was DECLARED at spec-time OQ-1 with clear AC-driven justification (AC line 1080 BYTE-IDENTICAL hint string mandate). Lesson: discipline + transparent deviation-adjudication beats either rigid no-new-classes OR ad-hoc registry growth. The Story 5.6 single-line CI gate is a structural enforcement that scales the discipline.

- **The dispatch-with-clear-file-lists pattern is dramatically faster than agent re-derivation**: 2 of 19 iterations (iter 9 Story 5.3 code-review; iter 16 Story 5.6 create-story) hit stream-idle-timeout on initial dispatch at ~14-19min wall-clock with NO outputs written. Both recovered cleanly via re-dispatch with TIGHTER SCOPE (focused file reads, single-pass quality gate verification, design directives in prompt). Iter 16's design directive (provided schema+resolver+CI-gate decisions in the prompt to avoid agent re-deriving them) reduced wall-clock from ~19min (timed out) to ~15min (success). Lesson: when an agent re-derives architectural decisions that the orchestrator already knows, tell it explicitly. Time saved compounds across iterations.

- **Single-/bmad-loop close is feasible for a 6-story epic with focused scope**: Epic 5 closed in **1 /bmad-loop invocation across 19 iterations** (vs Epic 4's 6 invocations across 30 iterations). The single-loop close is feasible when (a) all stories are well-specced upfront via Epic + Architecture documents; (b) stream-idle-timeout retries are recoverable via re-dispatch; (c) the 40-step effectiveMaxSteps cap provides margin. Recommended for future 4-7-story epics. Larger epics (10+ stories like Epic 4) may still benefit from multi-loop close to allow user check-in.

- **Two-layer CI-gate enforcement (unit + integration) protects contracts from regression**: Story 5.4 ships an integration-level test (`src/integration/escalate-actionable-hint.test.ts` PART 1 registry sweep over 17 classes) for the actionable-hint regex contract. Story 5.6 adds a COMPLEMENTARY unit-level test (`src/errors.test.ts:71-79` single-line constraint iterating all 17 codes). Both tests share the canonical `instances` array — when a new error class is added, BOTH gates fail. Lesson: pair integration-level "contract codification" tests with unit-level "field constraint" tests; share the canonical instances array between them.

- **Em-dash byte-verification at code-review prevents AC text drift**: Story 5.5's AC line 1123-1132 mandates the text "manual (interactive halt) — --resume available" with em-dash U+2014. Visual inspection cannot distinguish em-dash from en-dash from hyphen. Code-review verified literal byte-match `e2 80 94` at 2 sites. Lesson: when AC text contains non-ASCII characters (em-dash, en-dash, special quotes, etc.), require byte-verification at code-review. Add a `grep -c "<verbatim text>"` quality-gate step to dev/code-review for affected stories.
